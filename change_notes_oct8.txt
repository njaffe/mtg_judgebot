What each part does
- proxy/: a small FastAPI service that:
    - accepts /v1/chat/completions
    - routes to OpenAI/Anthropic (vendor switch)
    - logs latency/tokens/cost; exact-cache in Redis
- docker-compose.yml: runs redis, proxy, and your app (Streamlit/CLI)
- Dockerfile: two build targets: proxy and app
- .env.example: centralizes configuration, including USE_LLM_PROXY=true
- src/external/openai_client.py: single toggle for “direct OpenAI” vs “go through proxy”
- This is the only integration point your app surfaces (both Streamlit and CLI call this module)

src/core/synthesis_service.py

- Removed direct openai SDK usage and OpenAI() client construction.
- All LLM calls now go through openai_client.chat(...) (your adapter).
- If USE_LLM_PROXY=true, requests hit your FastAPI proxy and pick up Redis cache + metering + vendor routing.
- If USE_LLM_PROXY=false, the adapter calls OpenAI directly (preserving V1).
- synthesize_full_response now returns an extra llm_usage field (if available), which is handy for dashboards and cost/latency visibility.

## redis-makefile.yml
How this all works together
- redis starts first (cache + metrics storage).
- proxy starts next, connects to Redis, exposes /v1/chat/completions on port 8080.
- app starts last, runs Streamlit on port 8501.
- Your adapter (src/external/openai_client.py) sees USE_LLM_PROXY=true + PROXY_BASE_URL=http://proxy:8080 (internal service DNS), and routes LLM calls through the proxy.
- If you set USE_LLM_PROXY=false, the app calls OpenAI directly instead.
